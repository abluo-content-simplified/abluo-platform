Convention evidence (patch vs minor bump for features):
- Tags V1.0.3 through V1.0.13 (11 consecutive releases) are ALL third-number
  (patch-position) increments, regardless of change size. This includes
  substantive feature work tagged as patch bumps: V1.0.3 "Gallery Foundation
  — photoGallerySection, gallery + galleryItem schema...", V1.0.7 "ContentSection
  — add image field...", V1.0.8 "MediaContentSection — media positions, DS
  styles, CTAs, layout tokens". No V1.1.0 or V2.0.0 tag exists anywhere in the
  repo's tag history.
- CONCLUSION (Verified fact): the repo's ACTUAL convention is sequential
  patch-position increments for every release regardless of semver
  classification (feature vs fix). This diverges from CLAUDE.md's stated rule
  ("Versioning: semver... Tag format: V{major}.{minor}.{patch}"), which would
  imply a minor bump (V1.1.0) for a feature sprint. Since 100% of observed
  practice contradicts the documented semver-strict rule, I am reporting the
  divergence rather than silently picking a scheme.

PROPOSED VERSION: V1.0.14
  Rationale: continues the repo's actual, unbroken practice (11/11 recent
  releases patch-bump regardless of scope) rather than the documented-but-never
  -applied semver-minor rule. This is an AI recommendation, not a unilateral
  version-convention decision — see Open Decisions below.

VERSION SPLIT-BRAIN (I2) — NEW MECHANISM EVIDENCE (Verified fact, not fixed,
per pack's explicit "Tom decides — do not pick one" instruction):
  next.config.ts (lines 9-19) resolves the running platform's displayed version
  via:
    git describe --tags --abbrev=0 --match 'v[0-9]*'
  The code comment states this is INTENTIONAL: "matching lowercase v… tags only
  so historical uppercase V… tags are ignored" (introduced as part of "Release
  Automation v2", commit eef3ee0, tagged v1.0.2, 2026-06-28).
  Effect: because all 11 tags since v1.0.2 (V1.0.3 ... V1.0.13) use capital V,
  `git describe --match 'v[0-9]*'` cannot see them. The build silently falls
  back to the nearest matching lowercase tag, v1.0.2, meaning the deployed
  app's NEXT_PUBLIC_PLATFORM_VERSION / release title has been stuck reporting
  "v1.0.2 / Release Automation v2" through 11 subsequent real releases.
  This directly breaks the post-deploy truth-check invariant ("/api/version"
  == tag) described in the release-engineering pack, for every release since
  v1.0.2 — not just this one. This is a pre-existing condition, confirmed now
  with a concrete causal mechanism (previously I2 recorded the symptom; this
  adds the root cause). NOT introduced by this sprint. NOT fixed by this agent
  (out of scope; tag-convention resolution is Tom decides per pack).
  If V1.0.14 is tagged with a capital V (continuing current practice), the
  running app will continue to silently report "v1.0.2" and the post-deploy
  truth-check will keep failing silently until Tom resolves the tag-case
  convention (I2).
