# Supabase Backup & Recovery Guide
## Pre-Membership Migration — v0.9.0-foundation

**Supabase Project ID:** `xsdamzirepfqlutvqfbe`  
**Tables in scope:** `tenants`, `profiles`, `projects`, `leads`

## Prerequisites

You need one of:
- **Supabase CLI** (`brew install supabase/tap/supabase`) — recommended
- **`pg_dump`** — included in any PostgreSQL installation (`brew install postgresql`)

Get your database password from: Supabase dashboard → Project Settings → Database → Connection string. It looks like:

```

```

Store it as a shell variable for the session:

```bash
export SUPABASE_DB_URL="postgresql://postgres:[YOUR-PASSWORD]@db.xsdamzirepfqlutvqfbe.supabase.co:5432/postgres"
```

## 1. Export the Current Schema

### Option A — Supabase CLI (recommended)
```bash
supabase db dump \
  --db-url "$SUPABASE_DB_URL" \
  --schema public \
  --file backup/v0.9.0-foundation-schema.sql
```

### Option B — pg_dump
```bash
pg_dump "$SUPABASE_DB_URL" \
  --schema-only \
  --schema public \
  --no-owner \
  --no-acl \
  --file backup/v0.9.0-foundation-schema.sql
```

This captures all table definitions, indexes, constraints, RLS policies, and the `handle_new_user` trigger.

## 2. Export Table Data

Run each export separately so a failure in one does not affect the others.

```bash
mkdir -p backup/data

# tenants
pg_dump "$SUPABASE_DB_URL" \
  --data-only \
  --table public.tenants \
  --no-owner \
  --file backup/data/tenants.sql

# profiles
pg_dump "$SUPABASE_DB_URL" \
  --data-only \
  --table public.profiles \
  --no-owner \
  --file backup/data/profiles.sql

# projects
pg_dump "$SUPABASE_DB_URL" \
  --data-only \
  --table public.projects \
  --no-owner \
  --file backup/data/projects.sql

# leads
pg_dump "$SUPABASE_DB_URL" \
  --data-only \
  --table public.leads \
  --no-owner \
  --file backup/data/leads.sql
```

### Combined full backup (schema + all data)
```bash
pg_dump "$SUPABASE_DB_URL" \
  --schema public \
  --no-owner \
  --no-acl \
  --file backup/v0.9.0-foundation-full.sql
```

## 3. Verification Queries

Run these **before** the migration to confirm the backup files are complete and row counts match what is in the database. Open Supabase dashboard → SQL Editor.

```sql
-- Row counts at time of backup
select 'tenants'  as table_name, count(*) as rows from public.tenants
union all
select 'profiles',                count(*)         from public.profiles
union all
select 'projects',                count(*)         from public.projects
union all
select 'leads',                   count(*)         from public.leads;
```

```sql
-- Confirm tenant seed data is present
select id, slug, display_name, status, plan from public.tenants order by slug;
```

```sql
-- Confirm projects are linked to tenants correctly
select
  p.slug        as project_slug,
  t.slug        as tenant_slug,
  p.status,
  p.default_locale,
  p.custom_domain
from public.projects p
join public.tenants t on t.id = p.tenant_id
order by t.slug;
```

```sql
-- Confirm RLS is enabled on all tables
select tablename, rowsecurity
from pg_tables
where schemaname = 'public'
  and tablename in ('tenants', 'profiles', 'projects', 'leads');
-- All four rows should show rowsecurity = true
```

```sql
-- Confirm the signup trigger exists
select trigger_name, event_object_table, action_timing, event_manipulation
from information_schema.triggers
where trigger_name = 'on_auth_user_created';
-- Should return 1 row
```

Save the output of the row count query. After the migration, rerun it to confirm no data was lost.

## 4. Restore Procedure

Use this only if the migration causes data loss or corruption and you need to return to the v0.9.0-foundation state.

### Step 1 — Drop the damaged state
```sql
-- Run in Supabase SQL Editor
-- WARNING: this is destructive. Only run after confirming the backup files are intact.

drop table if exists public.tenant_members cascade; -- the new migration table, if partially created
-- Do NOT drop tenants/profiles/projects/leads unless they were corrupted
```

If tables themselves were corrupted or altered incorrectly:
```sql
drop table if exists public.leads    cascade;
drop table if exists public.projects cascade;
drop table if exists public.profiles cascade;
drop table if exists public.tenants  cascade;
```

### Step 2 — Restore schema
```bash
psql "$SUPABASE_DB_URL" --file backup/v0.9.0-foundation-schema.sql
```

Or paste the contents of `v0.9.0-foundation-schema.sql` directly into Supabase SQL Editor.

### Step 3 — Restore data (in dependency order)
```bash
# Restore in FK order: tenants first, then profiles/projects, then leads
psql "$SUPABASE_DB_URL" --file backup/data/tenants.sql
psql "$SUPABASE_DB_URL" --file backup/data/profiles.sql
psql "$SUPABASE_DB_URL" --file backup/data/projects.sql
psql "$SUPABASE_DB_URL" --file backup/data/leads.sql
```

### Step 4 — Verify restore
Rerun all four verification queries from Section 3. Row counts must match the values recorded before the migration.

### Step 5 — Restore application code
If a code change accompanied the migration:
```bash
git checkout v0.9.0-foundation
# or, to create a working branch from the checkpoint:
git checkout -b hotfix/rollback v0.9.0-foundation
```

## 5. Backup File Checklist

Before starting the migration, confirm all of these exist and are non-empty:

```bash
ls -lh backup/
ls -lh backup/data/

# Expected files:
# backup/v0.9.0-foundation-schema.sql     — full schema
# backup/v0.9.0-foundation-full.sql       — full schema + data (combined)
# backup/data/tenants.sql
# backup/data/profiles.sql
# backup/data/projects.sql
# backup/data/leads.sql
```

A zero-byte file means the export failed silently — do not proceed with the migration until all files have content.

## Notes

- Supabase also takes **automatic daily backups** (available in dashboard → Backups) on paid plans. These are a secondary safety net, not a replacement for this procedure.
- `auth.users` is in the `auth` schema and is not exported by the commands above. If you need to back up auth users, use Supabase dashboard → Authentication → Export users (CSV), or contact Supabase support for a full `auth` schema dump.
- The Sanity CMS data is independent of this backup. Sanity has its own document history per document and is not affected by Supabase migrations.
