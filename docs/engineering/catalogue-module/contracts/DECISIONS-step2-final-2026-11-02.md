# Catalogue V2 — step 2: Tom's final decisions (2026-11-02)

**Status: Decided — Tom, 2026-11-02.** This file is the authority for the Rev 3 contracts. Everything in `DECISIONS-step2-for-tom.md` is approved **as recommended** except where this file adds or changes something. Where wording here is precise, contracts use it verbatim.

## Blocking step 3

**D-1 Storage — Yes.** Module configuration for short settings: channels, currency, segment, public name, defaults and setup-completion state. One project document for Catalogue taxonomy; one for pack history; one for publication standards. Catalogue → Setup is the only normal editing area for all of them.

**D-2 Category storage — Yes.** One Catalogue taxonomy document per project, categories and tags stored as arrays. Retain: revision-guarded writes; atomic tree operations; stable immutable keys; cycle prevention; no map-shaped storage that could exhaust Sanity attribute paths; explicit handling of concurrent edits. Supersedes the Catalogue-specific part of Amendment J's one-record-per-term; other modules keep the generic taxonomy model.

**D-3 Category editing — Yes, option B.** Editors may: create categories inline while editing an item; rename and translate; reorder siblings; delete **unused** categories; manage tags. Setup permission is required for: moving categories between parents; reassigning items during deletion; deleting categories that are in use; editing channel-availability rules; applying starter packs. Catalogue → Setup → Categories & Tags is visible to people with either permission. Inline creation is an approved contextual entry point and **must call the same Catalogue taxonomy service as Setup** — not a second implementation. When creating inline the user can still choose the parent and see the complete category path. Amend K-4 and ADR-042.

*Unused (precise).* A category is unused only when it has: no assigned items, **including drafts**; no child categories; no automatic-listing references; no publication-standard or availability-policy references outside the category itself; no other stored Catalogue reference that would become broken by deletion. An editor may delete only a genuinely unreferenced **leaf** category. Otherwise deletion requires the Setup permission and a counted, previewed reassignment or cleanup operation.

**D-4 Website presence — Yes.** Lifecycle and visibility determine whether an item appears on the general website. Channel availability determines where it can be obtained, which prices apply and which availability labels are shown. An item unavailable through every active channel may still have an informational page or appear in the Catalogue. Hiding such items may come later as an explicit, opt-in website rule; never an implicit consequence of channel availability.

**D-5 Channel default — Yes.** One concept: `defaultAvailability` is the channel's runtime default. New items store no redundant channel values unless the user creates an explicit override. No `defaultChannelsForNewItems`.

**D-6 Time-based availability — CHANGED: build it now, separate from price windows.** Catalogue V2 supports both availability windows and price windows. A restaurant must be able to express: breakfast 07:00–11:00; a lunch menu only at lunchtime; delivery only in the evening; a dish unavailable on Sundays; a standard price that stays the same whenever the item is available.

Model: weekly availability schedules in the availability contract, reusing the existing time-zone, DST and overnight-interval semantics. Supports: a baseline availability state; optional scheduled overrides; days of the week; start and end times; overnight intervals; non-overlapping rules at the same scope; resolution at a supplied instant; existing precedence from project/channel default through primary category, item and format; an explanation of both the effective result and its source. Example: a Dinner category with baseline *unavailable* and a scheduled *available* override 18:00–23:00.

Price resolution stays independent: availability answers whether the item can be obtained at that moment; price windows answer which price applies at that moment; a missing price never means unavailable; a price never makes an item available. Automatic listings keep a real **"available now" / "available at this time"** filter (not "priced now"). This belongs in the contracts before the model migration.

1. **Schedules replace rather than merge, per channel.** For each channel, the most specific non-inherited rule supplies the **complete** availability rule and schedule for that channel. An item rule replaces the inherited category rule for that channel; a format rule replaces the item or category rule for that channel; rules for other channels are unaffected; "Use category default" restores inheritance of the complete upstream rule and schedule. A simple item-level "Available" therefore means available all week on that channel, even if the inherited category rule was 18:00–23:00 only. Each rule = baseline state + optional weekly scheduled overrides. Overlapping scheduled overrides at equal precedence are invalid.
2. **Collections never determine operational availability.** A Lunch collection is presentation; lunchtime availability belongs to a category, item or format rule. Scheduling the display of a collection/section is a separate presentation capability, not in this slice.
3. **Time does not hide an item page.** Lifecycle and visibility decide presence; the item page stays accessible; it can display its schedule; "available now" is calculated in the project time zone; structured data is unchanged and carries no schedule. **Invariant for anything claiming "available now":** evaluation always receives an explicit instant and project time zone; a cached result must never survive beyond the next relevant availability transition; browser or server must refresh/re-evaluate at that boundary; if the system cannot guarantee a current result it shows the schedule rather than an incorrect "available now". The automatic-listing contract chooses the caching implementation but must pass a **boundary test** proving a listing changes at the scheduled time without waiting for a long page-cache expiry.
4. **Weekly schedules only in this slice.** Date ranges, holidays, seasonal closures, exceptional dates later. Use an **extensible/discriminated schedule shape** so a dated exception can be added later without replacing the weekly model or migrating every rule.

**D-7 Equivalence — Yes, option B.** Compare old and new **public, visitor-visible outcomes** by item, context, channel and fixed instant; report price-window gap cases separately. Production has none, so its diff must be empty. Do not require two intentionally different internal resolvers to return identical internal objects.

**D-10 Migration default for channel projects — Yes.** Project default *unavailable* + explicit *available* rules for everything the old model considered sold. A migration must never make a new or existing item available through an additional channel.

**D-11 Rehearsal — Yes, in this order:** (1) deploy readers that accept both shapes; (2) export production Catalogue data; (3) rehearse the complete migration on `staging`; (4) produce equivalence and migration reports; (5) stop for approval; (6) run the production migration; (7) keep the export as rollback artefact. The staging rehearsal must not write to production.

**D-12 Public name — Yes to the copy and both public uses.** Where no public name exists, copy the localized `navLabel` into `publicName` and audit it. Approved: public name as the Catalogue landing-page title fallback; resolved public name (in the appropriate locale) as the `llms.txt` heading — for tmz this may become "Books"; an existing title such as "Between the Lines" continues to win wherever the site supplies it. Partial locales: normal locale fallback; discarded legacy values audited.

**D-13 Preset → pack — Yes, all four parts.** Convert tmz's `bookshop v1` record to pack history; offer the newer Bookshop pack as an optional non-destructive update; Bookshop's future default profile is Book; do not change tmz's existing profile automatically; replace the legacy `presetId` image-shape fallback before removing the field; ask for the public URL segment during module installation.

**D-14 Setup completion — Yes.** `setupCompletedAt` and `setupSource` stored separately from pack history. The item editor may read whether setup was completed, never which pack was applied. Starting empty, applying a pack or deliberately marking setup complete all satisfy it.

**D-15 Primary category and re-exposure — Yes, including the safety subset.** Primary category mandatory when publishing a new version; existing public items never silently unpublished; legacy multi-category drafts use the first existing category as primary. Back online, restore and date changes re-run **only** the safety subset: allergen review; option-choice allergen review; valid declaration shape; dangling or unresolved references. Ordinary quality requirements (image, description, placement) are not re-run on re-exposure.

## Later slices

**D-8 Missing price — Yes.** Website: recommended warning by default. Channel-specific delivery, priced export, PDF or marketplace output: required. Restaurant packs may propose website price required for food; the tenant can review that standard. A missing price never changes availability.

**D-9 Blocking outside the website — Yes.** A requirement blocks only its scoped action (e.g. a marketplace-image failure blocks that marketplace export, never the website or Catalogue availability).

**D-16 Allergen review — Yes, with clarifications.** `catalogue.allergen.update` for Owner, Site admin and Editor; never in support mode.
Reset when: the profile changes to Food or drink; an option-list attachment is added or replaced; a free-text add choice is added or materially edited; a choice changes from remove to add; a linked choice changes its target; a linked item's allergen declaration or relevant food profile changes; Contains / May contain / none-declared status or related declaration content changes outside the dedicated review action; future recipe, ingredient, supplier-label or technical-sheet data used as the review basis changes.
Do not reset for: name; description; price; images; categories; placement; translation-only edits.
The review service distinguishes a valid review action from an uncontrolled edit, so reviewing does not invalidate itself. Removing an option or detaching an option list does not by itself require a reset but is audited.
*Linked-item changes — timing:* editing only the linked item's draft does not affect live dependents; dependents are invalidated when the linked declaration **becomes effective through publication**; if linked item and parent are published together, the combined transaction performs the same invalidation and validation before committing; published parents stay online and keep resolving the linked item's current published allergens; a draft/review task is created or updated for every affected parent, marked `notReviewed`, shown clearly in the dashboard; each parent's next publication is blocked until sign-off is renewed; nothing is silently unpublished. If an affected parent has no draft, a draft is created from its published copy solely to carry the invalidation and review task, **identified as a system-created compliance task**, not an unexplained manual change.

**D-17 Overrides — Yes.** Only Owner and Site admin may override a recommended warning; record who, when and why; expires when the underlying meaning changes; required findings are never overridable.

**D-18 Studio limits — Yes.** Accept read-only Studio as a UI control, not a security boundary. Add restricted seats and tokens; detective webhook; daily reconciliation; audit events for writes outside the authorised gate; explicit break-glass. Correct ADR-032 D14 to say the protection is designed/documented until implemented.

**D-19 Atomic bulk publish — Yes.** `publishManyTogether` in the bulk slice: validate all documents and dependencies first; one transaction or nothing; respect the real payload limit; 100-document operational cap; calculate payload before attempting; refuse clearly when too large. Larger needs may use reviewed batches in the UI, never described as atomic.

**D-20 Retention — defer the exact duration** to the privacy/legal review; do not hard-code ten years. Must be decided before the first allergen-review evidence record is created in production, by jurisdiction, evidence purpose and privacy obligations. Until then: five years as platform audit default; longer allergen retention pending legal/privacy approval.

**D-21 Lower-impact confirmations — all approved**, with one naming change. Approved: implicit format has no explicit override; `effectiveIsbn` is the ISBN authority; editions do not become formats in this slice; conflicting duplicate rows → unset + visible readiness error, never an arbitrary winner; unknown-channel and stored-currency legacy rows stop pre-flight; unreachable standard prices retained until explicit cleanup; channel deletion requires counted, previewed, audited cleanup; packs reuse stable keys such as `dine-in` and `takeaway`; limits 12 channels, 24 formats per item, 300 categories, 200 Catalogue tags; readiness counts include drafts and distinguish Ready / Not yet; missing-translation checks only for public locales and not immediately penalising a newly added locale; superseded pricing sections in the brief clearly marked; export unavailable in support mode.
*Option-item picker:* keep the rule that a linked item must have at least one price; rename the internal result from `offered` to **`hasPrice`**; message: **"This item needs at least one price before it can be used as a linked choice."** An item with at least one price qualifies even when unavailable on a particular channel. All other picker requirements (project scope, valid draft/published dependency, lifecycle checks) continue to apply. After the split, "offered" is never a synonym for "priced".
