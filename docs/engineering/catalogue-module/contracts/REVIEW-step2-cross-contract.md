## (B) Cross-contract contradictions — each with one recommended resolution

**X-1 Channel rule row shape.** [A] C5-7 / C3-3: `catalogueChannelRule { _key, _type, channel, state }`, and [A] Interfaces asks C1 to use it. [B] C1.4: `channelRules? array of { _key: <channelKey>, channel, rule }`. → **Use [A]'s `catalogueChannelRule { _key, _type, channel, state }` everywhere** (one validator, `availabilityRowIssues`), `_key` = channel key at category level for addressable patches.

**X-2 Vocabulary names for the same concepts.** Tri-state: [A] `AvailabilityRuleValue` vs [B] `ChannelRule`/`ChannelRules`. Channel: [A] `Channel` (order = array position) vs [B] `ChannelObject` "(… `active`, `order`)" vs [C] `ServiceChannel`. Category node: [A] C5-2 redefines `CategoryNode` ("From C1, assumed") with a subset of [B] C1.3's fields. Availability result: [A] `AvailabilityExplanation`/`explainAvailability`/`availabilityMatrix` vs [C] §6.2/6.14 `EffectiveAvailability`/`effectiveAvailability(item, format, context)`. → **Owner names win:** C1 owns `CategoryNode`, `CategoryKey`, `TagKey`; C2 owns `Channel`, `ChannelKey`, `AvailabilityRuleValue`, `AvailabilityState`; C5 owns `AvailabilityExplanation`. [A] imports `CategoryNode` from C1 instead of redefining it; [B] drops `ChannelRule`/`ChannelObject`; [C] replaces `ServiceChannel`/`EffectiveAvailability`/`effectiveAvailability` by the C2/C5 names. One `commerce-types.ts` re-exports them.

**X-3 Two implementations of the primary-path walk.** [A] C5-3 walks `primaryPath(...).keys` itself and needs a C1 `primaryPath(tree,key) → path|none|broken{missingCategory|cycle}`. [B] C1.6 provides no `primaryPath`; it provides `categoryChannelRule` (nearest non-inherit on the primary path) and `buildTree` *repairs* cycles/orphans (orphan becomes a root, cycle edge cut) — so "broken" can never be observed. Violates K-9 "one implementation per concept". → **C1 adds `primaryPath(tree, key): PrimaryPath` (returning `broken` when `tree.issues` touch the path); C5 uses only `categoryChannelRule` for L1 and `primaryPath` for the source path/explanation.** C5 does not walk the tree.

**X-4 Readiness inputs vs C4/C5 outputs.** [C] `PriceCoverage = 'full' | 'windowedOnly' | 'none'`; [A] `priceCoverage(format, ctx, channels) → {kind:'full'} | {kind:'partial', gaps} | {kind:'none'}` — different values **and** different meaning ([C] "price only inside windows, no standard fallback"; [A] "gaps in the week"). Issue codes: [A] `price.missing`, `price.partialCoverage`, `price.ambiguous`, `price.indeterminate`, `price.inactiveChannel`, `availability.primaryCategoryBroken`, `availability.conflictingRows`, `format.skuDuplicateInProject`, `legacy.offersShadowed` are declared "readiness issues, C6" — **none exists in [C]'s `ReadinessCode` registry**; [C] has `priceMissing`, `pricePartial`, `price.invalid/.times/.overlap/.channel` (legacy offer grouping). → **[C] consumes [A]'s `priceCoverage` return type unchanged (`pricePartial` ⇔ `kind:'partial'`) and adds registry rows for every code [A] hands to C6: `price.ambiguous` (R everywhere), `price.indeterminate` (R, gate), `availability.conflictingRows` (R), `availability.primaryCategoryBroken` (→ same row as `primaryCategoryMissing`, see X-5), `format.skuDuplicateInProject` (r), `price.inactiveChannel` (r), `legacy.offersShadowed` (integrity). [A]'s save-time `format.*`/`price.*` codes map to [C] rule 3 by one table owned by [C].**

**X-5 Unknown/broken primary category: visible or hidden?** [B] C1.6: `unknown_primary` → Required `primary_category` finding (visible, message distinguishes); [A] C5-3: `primaryCategoryBroken` "C6 turns it into a readiness error"; [C] §6.7.3: `integrity.unknownCategory` — gate-only, `fix: none`, never shown in the editor. [B] also maps `archived_primary` → Recommended; [C] has no such rule. → **Standard family, visible: `primaryCategoryMissing` covers `no_primary ∪ unknown_primary ∪ broken path` with a `values.reason`; add `primaryCategoryArchived` (r). `integrity.unknownCategory` stays only for additional-category keys.** [C] calls C1's `categoryAssignmentState` rather than reading item fields (as [B] states).

**X-6 Context naming: `website` vs `general`.** [C] `PublicationContext {kind:'website'}`; [A] `OfferingContext {kind:'general'}` for the same no-channel/any-channel website question. → **Keep both types (they answer different questions) but [C] defines one pure `offeringContextOf(ctx: PublicationContext): OfferingContext` (`website`→`general`, `channel`→`channel`, `print/marketplace` with channel → that channel, else `general`) in `readiness/`**, and fixtures R-08…R-13 state the mapping.

**X-7 Storage story — there is not yet one.** [A] C2-3: channels and `formatTemplates` in **module config**, *no* `catalogueSettings` document. [B] C11.2: `publicName` in module config "unless C2 moves settings"; C7.9 `setupCompletedAt` "in Catalogue settings" (container unnamed); C7.5 history in its own document `catalogue-packs.<slug>` (justified by the false F7 premise, see A6); C1 taxonomy in `catalogue-taxonomy.<slug>`. ## (C) Flaws in individual contracts

**[A] C2–C5, C10**
- C-1 **C10-3 majority default changes the future.** `legacyAvailability` sets `defaults[c]` by majority; in a channel project where most items had an unscoped offer, `defaults[c]='available'` means **new** items become available on `c` with no price — the old model would not supply them. Exact for existing items, not for future ones (brief §27 "defaults must never silently make items available"). Prod unaffected (no channels). Fix: default `unavailable` unless *every* item was sold on `c`, or state the change and ask Tom (D-10).

## (D) Decisions only Tom can take — merged and deduplicated

Ordered by how much they block the **model slice** (K-9 step 3). Each: options → recommendation. Source issues in brackets.

1. **Storage story (X-7).** (a) everything in module config; (b) a `catalogueSettings` document; (c) module config for settings + own documents for taxonomy, pack history, publication standards. → **(c).** Amends D3's "becomes a document type" trigger for channels explicitly. [A T-3; B Issue 13; C I-5]
2. **Category storage: one document per project vs one record per node (K-4 "J's guarantees").** (a) extend `taxonomyTerm` + parent/rules; (b) Catalogue-owned per-node documents; (c) one `catalogueTaxonomy` document per project. → **(c)** — atomic tree writes, cycle safety, pack atomicity; fits Sanity limits with array storage (A8).
