# Release Automation

Developer tooling for cutting Abluo releases safely and repeatably. This document
explains **how the tooling works**. For the step-by-step **release procedure**
(what to run, in what order), see [`release-workflow.md`](./release-workflow.md).

---

## Version model (single source of truth)

Abluo has **one version**: the **Platform Version**, carried by an **annotated git
tag**. The tag is the single source of truth.

- **Tag name = the version** — lowercase, e.g. `v1.0.2`. Exactly three numeric
  segments (`vX.Y.Z`). Uppercase `V` and four-segment forms (`v1.0.0.2`) are
  rejected by the release script.
- **Tag message = the release title** — e.g. `Location Platform` (optional).

There is **no engineering version**. A specific build is identified by its
**build metadata** — commit SHA, branch, environment, and build time — which
together uniquely pin any build. No `vX.Y.Z.N` numbers exist anymore.

Historical uppercase tags (`V0.9.24`, `V1.0.0`, …) are left untouched; version
derivation matches lowercase `v…` tags only, so the cutover is clean and no
history is rewritten. The v2 baseline is **`v1.0.1`**.

### How the tag flows into the app

```
annotated git tag  (v1.0.2, message = "Location Platform")   ← source of truth
        │  read at build time (git describe), release.json fallback
        ▼
next.config.ts  →  NEXT_PUBLIC_*  →  /api/version  →  CMS version dialog
        ▲
Vercel build env (commit, branch, env) + build timestamp     ← build metadata
```

`next.config.ts` resolves the version at build time:
1. **Preferred:** `git describe --tags --abbrev=0 --match 'v[0-9]*'` for the
   version, and the tag's subject line for the title.
2. **Fallback:** the generated `release.json` cache, used when tags aren't
   visible (e.g. a shallow CI clone).

### release.json — a generated cache, not a source

`release.json` is **generated by `release.sh`** from the tag and committed as a
build-time fallback. **It must never be hand-edited.** Shape:

```json
{
  "version": "v1.0.1",
  "title": "Repository recovery baseline",
  "releasedAt": "2026-06-28"
}
```

`package.json` `version` is also synced (without the leading `v`, e.g. `1.0.1`)
as a convenience mirror for tooling. Neither file is authoritative — the tag is.

## Scripts

```
scripts/
  doctor.sh      # repository health checks + version-consistency checks
  release.sh     # cut a release (the only release command)
  lib/
    common.sh    # shared helpers: colours, logging, git, lock-safety, version SSOT
```

POSIX-friendly shell, `set -euo pipefail`, sourcing `lib/common.sh`. `release.json`
access and `package.json` sync use `node` (already a repo dependency).

---

## `release.sh`

```bash
./scripts/release.sh v1.0.2 "Location Platform"   # version + title
./scripts/release.sh v1.0.2                        # title optional
./scripts/release.sh                               # interactive prompts
./scripts/release.sh v1.0.2 --dry-run             # show steps, change nothing
```

It prompts for only two things — **Platform Version** (required, validated
lowercase `vX.Y.Z`) and **Release Title** (optional). Then, automatically:

| Step | Action | Stops if… |
|---|---|---|
| 1 | `doctor.sh` health checks | repo unhealthy |
| 2 | Verify the tag is unused (local + remote) | tag exists |
| 3 | Regenerate `release.json` + sync `package.json` | — |
| 4 | Deterministic build gate (`rm -rf .next` + build) | build fails |
| 5 | Create the **release-marker commit** `release: v1.0.2 - Location Platform` | — |
| 6 | Create the **annotated tag** (message = title) | — |
| 7 | Push the branch and **only** the new tag (never `--tags`) | push fails |
| 8 | Verify commit/tag/remote consistency | inconsistent |
| 9 | Structured summary | — |

Steps 1–4 make no commit; `--dry-run` stops after the build and prints the exact
git commands it would run. If no title is given, the commit is `release: v1.0.2`
and the tag message is the version itself.

The deployment pipeline is unchanged: you cut the release on `dev`, then promote
`dev → preview → production` as usual (see the workflow doc). The release-marker
commit travels through the promotion, so Vercel deployments read as releases.

## `doctor.sh`

Read-only health checks (run standalone, or by `release.sh` first). Critical
checks: git installed, on `dev`, no stale `HEAD.lock`, no merge/rebase in
progress, `origin` reachable, branch in sync. Plus **version consistency**: the
current lowercase tag, and whether `release.json` / `package.json` match it
(warnings only — both are regenerated on the next release). Exit `0` = healthy.

---

## Vercel deployments

Releases use a **release-marker commit** (`release: v1.0.2 - Location Platform`).
Because Vercel titles deployments by the tip commit message, Preview and
Production deployments read as releases while the underlying feature commits stay
intact in git history. No Vercel configuration changes are required, and the
`dev → preview → production` branch pipeline is unchanged.

## Troubleshooting

**`'vX' is not a valid release version`** — use lowercase `vX.Y.Z` (e.g. `v1.0.2`).
Uppercase `V` and four-segment versions are rejected by design.

**`Tag 'v1.0.2' already exists`** — that version is taken; pick the next one.

**`Build failed`** — `npm run build` didn't pass; nothing was committed. The gate
always removes `.next` first for a deterministic build.

**Stale `*.lock` in `.git`** — if git refuses with "Unable to create … .lock",
no git process is running, remove the stale lock(s): `find .git -name '*.lock' -delete`.

**`Current branch is 'X', expected 'dev'`** → `git checkout dev`.

**Pushes** must run from your terminal (GitHub auth).

## Migration from the dual-version model (v1.2 → v2)

- Removed the **engineering version** entirely (`vX.Y.Z.N`) and `milestone.sh`.
- `release.sh` is now the single release command (the old `eng`/phase/`next`/
  `status` modes and roadmap parsing are gone).
- `release.json` changed shape (`version` / `title`) and is now a **generated
  cache**, not an authoritative SSOT — the git tag is.
- `/api/version` drops `engineeringVersion`/`releaseName`; returns `platformVersion`,
  `releaseTitle`, and an **ISO** `buildDate` (the CMS formats it in local time).
- New releases use lowercase tags; historical uppercase tags are untouched.

## Design notes

- **The git tag is the source of truth.** `release.json` and `package.json` are
  generated mirrors; humans never edit them.
- **Helpers live in `lib/common.sh`** (`is_release_version`,
  `current_release_version`, `tag_title`, `generate_release_json`,
  `sync_package_version`, plus colours/logging/git/lock-safety).
- **Deterministic build:** `rm -rf .next` before every release build.
- **No `git push --tags`, ever** — only the named release tag is pushed.
- **Annotated tags only.**
